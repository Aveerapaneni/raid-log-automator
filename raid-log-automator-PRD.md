# RAID Log Automator — Product Requirements Document

**Author:** Asha Veerpaneni — Program Manager / Scrum Master
**Status:** Draft v1
**Last updated:** August 14, 2026

## 1. Problem Statement
Risks, assumptions, issues, and dependencies are usually tracked manually in a spreadsheet, reviewed inconsistently, and rely on the PM remembering to enforce discipline (naming an owner, requiring a mitigation plan, converting a materialized risk into an issue, escalating aging items). This project automates the mechanical, rule-based parts of maintaining a RAID log — scoring, validation, aging, escalation, category discipline, and readiness queuing — using mock data, while the PM and stakeholders remain the decision-makers on what actually gets done about each item.

## 2. Goals
1. **Learning goal:** Apply what was learned building the Sprint Planning Automator to a second, independent domain — reinforcing Claude Code, Python, and git skills through repetition rather than starting from zero.
2. **Career goal:** Produce a second standalone portfolio project — independently runnable, independently postable on LinkedIn — that demonstrates breadth (a second PM artifact automated, not just the same idea repeated).
3. **Cost-fluency goal:** Understand exactly where AI/API usage would introduce cost beyond the existing Claude Pro subscription, and design v1 to avoid any such cost entirely.

## 3. Users
- **Primary user:** Program Manager (you) — maintains the RAID log, sets escalation thresholds, triggers digests on demand.
- **Secondary stakeholders:** Item owners (team members) — responsible for mitigation plans and status updates on their entries. Leadership/stakeholders — receive the digest when the PM chooses to generate one.

## 4. Design Decisions Carried From Project Planning

These decisions came directly out of planning discussion and constrain everything below — flagged here so they aren't lost during the build.

**4.1 — Data independence.** This project uses its own mock dataset (`raid_mock_data.json`), created independently and **not derived from, or dependent on, `mock_jira_data.json`** from the Sprint Planning Automator project. The two repos must each run standalone with no cross-repo file requirement, so they can be showcased as separate, independent LinkedIn posts.

**4.2 — No cost beyond the existing Claude Pro subscription.** Everything in this project must run using only the already-paid $20/month Claude Pro plan — via Claude Code sessions, the same way the Sprint Planning Automator was built. The script itself must **not** require a separate Anthropic API key or make autonomous, pay-per-token API calls at runtime. Any AI-assisted text (e.g. a digest summary) is generated by asking Claude Code directly during an interactive session — a human-driven step, covered under Pro — rather than code that calls the API on its own.

**4.3 — "Sprint Ready pile" is reused as a name only, not a dependency.** US-8 below borrows the name "Sprint Ready pile" from the Sprint Planning Automator project because the concept — a prioritized queue of fully-groomed, unblocked items — is genuinely analogous. This was a deliberate decision: **the name is shared intentionally, but the implementation is entirely self-contained** within this project's own data and logic. There is no code or data dependency on the Sprint Planning Automator repo, and no import/export between the two. Anyone reading both projects should understand this as two independent tools that happen to use a similar pattern, not one relying on the other.

## 5. Data Schema (mock RAID entries)

**In a real enterprise JIRA tool**, most fields below would be entered manually by the PM/PO/team during refinement or triage sessions — that's the real-world workflow this project is modeling. **For this project specifically**, since we're working entirely from mock data, no manual entry step exists in v1: every field is pre-populated as part of generating `raid_mock_data.json`, and the automation logic operates on that pre-populated dataset directly. The table below tags each field with how it would originate in a real tool (for your own reference), while noting that here, all of it is generated as mock data up front.

To properly exercise the validation logic in US-2, the mock dataset should deliberately include a mix — some entries with every field complete, and a few with fields intentionally left blank (missing Owner, missing Mitigation Plan, etc.) — so the flagging behavior has something real to catch.

| Field | In a real enterprise tool | In this project |
|---|---|---|
| ID | Auto-generated by JIRA | Pre-populated in mock data |
| Category | Manually entered | Pre-populated in mock data |
| Description | Manually entered | Pre-populated in mock data |
| Date Raised | Manually entered | Pre-populated in mock data — used for aging and tie-breaking (US-8) |
| Owner | Manually entered | Pre-populated in mock data — required, a named individual, never a team |
| Probability (1-5) | Manually entered | Pre-populated in mock data — required for Risk/Assumption/Dependency; optional for Issue |
| Impact (1-5) | Manually entered | Pre-populated in mock data — required for all categories |
| **Priority** | Calculated | **Calculated** — = Probability x Impact, bucketed Low (<8) / Medium (8-14) / High (15+). Not a separate manually-entered field — confirmed during planning. |
| Mitigation / Response Plan | Manually entered | Pre-populated in mock data — required for Risk and Issue entries |
| Start Date | Manually entered | Pre-populated in mock data — when set, Status automatically moves to "In Progress" |
| Status | Manually entered + calculated | Pre-populated (initial value) + calculated — Not Started / In Progress / Monitoring / Escalated / Closed. Escalated is set automatically (US-4). |
| Materialized flag | Manually entered | Pre-populated in mock data — boolean, applies to Risk entries only; true triggers auto-conversion to Issue (US-5) |
| Dependency links | Manually entered | Pre-populated in mock data — IDs of other entries this item depends on, if any |
| Blocked flag / links | Manually entered | Pre-populated in mock data — IDs of entries currently blocking this one, if any |
| Target Date | Manually entered | Pre-populated in mock data |
| Last Updated | Manually entered | Pre-populated in mock data |

## 6. Scope

### In scope (v1)
- Independent mock JSON dataset representing RAID log entries, matching the schema in Section 5
- Auto-calculate Priority (Probability x Impact) and bucket as Low/Medium/High, matching the earlier xlsx template's thresholds
- Validate entries against log discipline rules: reject or flag any entry missing a named Owner; reject or flag any Risk/Issue missing a Mitigation Plan; allow Probability to be blank only for Issues
- Auto-calculate Days Open from Date Raised; blank once Status is Closed
- Auto-set Status to "In Progress" when Start Date is entered
- **Configurable escalation threshold at runtime:** the PM supplies the score-band and days-open threshold each time the tool runs (e.g. as a command-line input or prompt), rather than a hardcoded value — since priority can shift with ad hoc initiatives
- Category conversion: when a Risk's Materialized flag is set true, auto-convert it to an Issue, preserving its ID and history rather than creating a duplicate entry
- **Manually-triggered digest:** generate a plain-English summary of the top 3-5 highest-priority open items, grouped by category, only when the PM explicitly runs the digest command — not on an automatic schedule
- **Sprint Ready pile (self-contained, see Section 4.3):** promote entries with complete required information and no active Blocked flag into a prioritized queue. Unscored Issues (blank Probability, per Section 9) sit at the very top — they are live, active problems and take precedence over any scored item — ordered among themselves by Date Raised (earliest first). Below them, scored entries are ordered by Priority (High to Low), with ties broken by Date Raised (earliest first)
- Never delete entries — Closed items remain in the dataset, excluded from the active digest but still present
- Runs from the terminal (CLI), no graphical interface required for v1

### Out of scope (v1)
- Any integration with, or dependency on, the Sprint Planning Automator's mock data or code (see Section 4.1, 4.3)
- Autonomous/live Claude API calls made by the script itself (see Section 4.2)
- Automatic/scheduled digest generation (see US-6 — this is manual-only in v1)
- Real notifications (email/Slack)
- Multi-user auth/permissions
- Editing the actual `RAID-log-template.xlsx` file directly (v1 uses JSON only)

### Possible v2 (after v1 works)
- ~~Persistence across runs~~ — scoped, see Section 13.
- AI-generated digest narrative via a live API call — only if explicitly revisited as a cost decision, with a separate API key. Not yet scoped.
- Automating directly against the xlsx template using openpyxl, instead of or alongside JSON. Not yet scoped.
- A deliberate, explicitly-scoped integration project genuinely connecting this tool with the Sprint Planning Automator, built as its own follow-up. Not yet scoped — on hold pending a look at that repo's actual schema.

## 7. User Stories & Acceptance Criteria

**US-1:** As a Program Manager, I want new entries auto-scored and bucketed, so I don't calculate priority manually.
- *Acceptance:* Given Probability and Impact values, Priority = Probability x Impact is computed; bucket assigned as Low (<8), Medium (8-14), or High (15+).

**US-2:** As a Program Manager, I want entries validated against log discipline rules, so incomplete entries don't silently enter the log.
- *Acceptance:* An entry missing an Owner is flagged. A Risk or Issue missing a Mitigation Plan is flagged. Probability may be blank only when Category is Issue; any other missing Probability is flagged.

**US-3:** As a Program Manager, I want Days Open and Status calculated/updated automatically from dates, so tracking doesn't require manual upkeep.
- *Acceptance:* Days Open = current date minus Date Raised; blank whenever Status is Closed. Status automatically becomes "In Progress" the moment Start Date is set. This promotion is one-way and only fires from "Not Started" — it never overwrites Monitoring, Escalated, or Closed, even if Start Date is present, since those later-stage statuses are owned by other stories (US-4, US-7) and shouldn't be silently reset backward.

**US-4:** As a Program Manager, I want the escalation threshold configurable at runtime, so I can adjust it when ad hoc initiatives change what counts as urgent.
- *Acceptance:* Each time the tool runs its escalation check, it accepts a score-band and days-open threshold as input (not a hardcoded constant). Status auto-updates to "Escalated" for any item breaching the supplied threshold, and the change is logged with a timestamp. The check is idempotent: an entry already Escalated (or Closed) never re-triggers or re-logs on a later run, even if it still breaches the threshold — this mirrors the idempotency requirement Section 9 states explicitly for US-5's Materialized-Risk conversion.

**US-5:** As a Program Manager, I want a materialized Risk to automatically convert to an Issue, so category discipline is enforced without manual cleanup.
- *Acceptance:* When a Risk entry's Materialized flag is set to true, its Category updates to Issue in place — same ID, history preserved — rather than a new entry being created.

**US-6:** As a Program Manager, I want to trigger the digest manually whenever I need it, rather than on a fixed schedule.
- *Acceptance:* The tool only generates the top 3-5 priority open items summary, grouped by category, when explicitly invoked by the PM (e.g. a specific command). No automatic or time-based trigger exists in v1. An unscored-but-valid open item (e.g. an Issue with blank Probability) is eligible for the top 3-5 and ranks ahead of every scored item, ordered by Date Raised among themselves — the same precedence rule as the Sprint Ready pile (US-8), since a live, active problem shouldn't be buried by items that merely scored higher.

**US-7:** As a Program Manager, I want closed items retained rather than deleted, so the historical record stays intact.
- *Acceptance:* Status can be set to Closed, but no entry is ever removed from the dataset; Closed items are excluded from the active digest but remain present and queryable. Removal is refused for any entry regardless of Status, not just Closed ones — Section 9's "Closed entry" wording is the specific case a PM would most plausibly try, but Section 6's "never delete entries" rule is unconditional, so the refusal generalizes to all statuses.

**US-8:** As a Program Manager, I want fully-groomed, unblocked items automatically queued into a prioritized "Sprint Ready pile," so I know which items are ready to bring into planning discussions.
- *Acceptance:* An entry is added to the Sprint Ready pile only if all required fields for its category are complete (Owner, Mitigation Plan where applicable, Impact, Probability where applicable, Start Date), it has no active Blocked flag, and its Status is not Closed (a Closed item has nothing left to bring into a planning discussion — same reasoning as US-7 excluding Closed items from the active digest). An Issue with blank Probability is eligible (Probability is not required for Issue) even though it has no computable Priority. Ordering: unscored Issues are placed first, ahead of all scored entries, ordered among themselves by Date Raised (earliest first) — since a live, active Issue takes precedence over a scored item awaiting action. Scored entries follow, ordered top-to-bottom by Priority bucket (High, then Medium, then Low); when two scored entries share the same Priority, the one with the earlier Date Raised is placed first. This queue is built entirely from this project's own data (see Section 4.3) — no dependency on the Sprint Planning Automator repo.

## 8. Non-Functional Requirements
- **Performance:** Process the full mock dataset (~20-50 entries) in under 5 seconds.
- **Cost:** v1 must run with zero dependency on a paid Anthropic API key or autonomous API calls — see Section 4.2. This is a hard constraint, not a preference.
- **Independence:** This repo and its mock dataset must run standalone, with no requirement to clone or reference the Sprint Planning Automator repo — see Section 4.1 and 4.3.
- **Usability:** Digest output must be understandable by a non-technical stakeholder without reading any code.
- **Reliability:** Must handle the edge cases in Section 9 without crashing.

## 9. Risks & Edge Cases
- Entry missing Owner or Mitigation Plan → flagged explicitly, not silently accepted into the "clean" log.
- A Risk marked materialized more than once (e.g. reprocessed) → conversion must be idempotent; no duplicate Issue created on a second run.
- No escalation threshold supplied at runtime → tool should prompt for one or refuse to run the escalation check, rather than silently defaulting.
- Attempt to delete or hard-remove a Closed entry → disallowed; the tool should refuse and explain why.
- Missing Impact, or missing Probability on a non-Issue entry, or an out-of-range (not 1-5) Probability/Impact value → entry flagged as incomplete and excluded from scoring until corrected.
- Issue with blank Probability → valid per US-2 (not flagged as incomplete) and still excluded from Priority scoring, since Priority = Probability x Impact cannot be computed without both values. Validity and scorability are separate checks. It remains eligible for the Sprint Ready pile (Section 6, US-8) and is placed ahead of all scored entries there, since a live, active Issue takes precedence over a scored item awaiting action.
- No entries qualify for the Sprint Ready pile → tool reports an empty queue clearly, rather than erroring.
- Two entries tie on both Priority and Date Raised → order is stable but arbitrary; flagged in output as a true tie for the PM's attention.

## 10. Success Metrics
- 100% of entries with missing Owner/Mitigation Plan correctly flagged against the mock dataset's known incomplete entries.
- 100% of escalation triggers match expected outcomes against the runtime-supplied threshold on the mock dataset.
- Sprint Ready pile ordering matches expected Priority-then-Date-Raised ordering on the mock dataset, 100% of the time.
- End-to-end run completes within the 5-second performance target (Section 8).
- Zero paid API calls required to run the core script, verified by running it with no Anthropic API key configured.

## 11. Technical Approach (initial)
- Mock data stored as JSON (`raid_mock_data.json`), created independently per Section 4.1 — no shared file or cross-repo dependency with the Sprint Planning Automator.
- Core logic built and tested as a terminal/CLI Python script, run through Claude Code under the existing Pro subscription.
- Escalation threshold and digest generation are both explicit, PM-triggered actions — no background scheduling in v1.
- Sprint Ready pile logic lives entirely within this project's code and data (Section 4.3).
- Git used from the first commit, pushed to its own public GitHub repo (e.g. `raid-log-automator`), cross-linked in both READMEs to the Sprint Planning Automator repo per the portfolio strategy — links only, no code or data dependency.
- No external network calls required to run the core script.

## 13. v2 Scope — Persistent Storage

### 13.1 Problem
v1 treats `raid_mock_data.json` as an immutable snapshot: every command loads it fresh and computes everything from scratch, so nothing a PM does — closing an item, escalating it, materializing a risk — survives past that single run. Running `escalate` twice produces the same result twice instead of a real "already handled" state. This was fine for demonstrating the rule-based logic (v1's actual goal), but not for anyone who'd want to actually use this day to day.

### 13.2 Goal
Make state changes persist between separate invocations of the tool, so the log reflects its current true state rather than resetting to the original mock snapshot every run.

### 13.3 Design Decisions
- **Local-only, not shared.** The persistent store (`raid_log.db`, SQLite) belongs to this project alone. It creates no dependency on, and no shared access with, the Sprint Planning Automator repo — a shared database would violate Section 4.1/4.3's independence guarantee. If a future integration project (still unscoped, see Section 6) wants to correlate data across the two tools, it will read from each project's own store via a separate connector, not through one shared database.
- **`raid_mock_data.json` stays the canonical seed, not a live file.** The tool never overwrites it. It remains the portable, independently-reviewable mock dataset described in Section 4.1 — what a portfolio reviewer sees without running any code — and is also the source used to (re-)seed the database.
- **No new cost.** `sqlite3` is part of Python's standard library — no external service, no API, no separate install. This doesn't touch the zero-cost constraint from Section 4.2.
- **Calculated fields are still never stored.** Priority and Days Open remain computed fresh on every read from Probability/Impact/Date Raised, exactly as in v1 (Section 5) — storing them would risk staleness (Days Open would be wrong the moment a day passes). Only the fields v1's user stories actually transition — Status, Category, Materialized — are ever written back by the tool.

### 13.4 Storage
- `raid_log.db`, auto-created and seeded from `raid_mock_data.json` the first time any command runs against a path where it doesn't yet exist.
- One `entries` table, columns matching the raw/input fields from the Section 5 schema (`dependency_links` and `blocked_by` stored as JSON-encoded text, since SQLite has no native array type).
- A `reset-db` command re-seeds the database from `raid_mock_data.json`, discarding all persisted state. This is an explicit, clearly-named action only — never a side effect of a normal run, mirroring the same "explicit refusal/action over silent surprise" philosophy already used for escalation thresholds (US-4) and entry removal (US-7).

### 13.5 User Stories & Acceptance Criteria

**US-9:** As a Program Manager, I want the tool's state changes to persist between separate runs, so a status I set, an escalation that fired, or a risk that materialized stays that way the next time I open the tool — rather than resetting to the original mock data every time.
- *Acceptance:* Every mutating operation already defined in v1 — Status auto-transition (US-3), Escalation (US-4), Materialized-Risk conversion (US-5), and Close (US-7) — writes its result to `raid_log.db`, not just to an in-memory copy for that run. Running the same command twice in two separate invocations reflects the first run's result on the second (e.g. an already-Escalated entry stays Escalated and is not re-logged, proving the existing idempotency guarantee — previously only provable within a single run — now holds across real separate process invocations too).

**US-10:** As a Program Manager, I want an explicit way to reset the database back to the original mock dataset, so I can start over for a demo or after testing without hand-editing anything.
- *Acceptance:* A dedicated command (`raid_tool.py reset-db`) re-seeds `raid_log.db` from `raid_mock_data.json`, discarding all persisted state. This never happens as a side effect of any other command. `raid_mock_data.json` itself is never modified by this or any other operation.

### 13.6 Edge Cases
- Command run before `raid_log.db` exists → auto-created and seeded from `raid_mock_data.json`, not an error.
- `reset-db` run when `raid_log.db` doesn't exist yet → same as a fresh seed; not an error.
- The "never delete" guarantee (US-7) extends to the database layer: `remove_entry` refuses regardless of persistence, and no code path in this scope ever issues a `DELETE` against the `entries` table.
- Concurrent runs (two terminals writing at once) are out of scope — this remains a single-PM, single-session CLI tool; SQLite's default locking behavior is sufficient without any special handling.

### 13.7 Definition of Done (v2 — persistence)
- `raid_log.db` created and seeded automatically on first use.
- US-9 and US-10 acceptance criteria pass, with the idempotency guarantee demonstrated across two genuinely separate process invocations (not just two calls within one Python process, as v1's tests necessarily did).
- All v1 tests and behavior continue to pass unchanged — persistence is additive, not a rewrite of v1's logic.
- README updated with the new storage model and the `reset-db` command.
